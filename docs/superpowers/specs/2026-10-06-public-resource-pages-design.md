# Public Resource Pages (services, invoices, receipts, bookings) — Design

**Date:** 2026-10-06
**Status:** Approved design, pending implementation plan

## Summary

Customers already reach three public pages: a service's booking flow at `/book/<slug>`, and
invoice and receipt links at `/i/<slug>/<key>` and `/r/<slug>/<key>`. Bookings have no page of
their own, and the four kinds of record live under four unrelated URL shapes.

This design gives every customer-facing record one public page under the same name the
owner uses for it in the dashboard, each with its own link preview card:

| URL | Page | Share card |
| --- | --- | --- |
| `/services/<slug>` | Service profile; "Book a time" hands off to the unchanged `/book/<slug>` | `serviceCard` (today's `/book` card, extracted) |
| `/invoices/<publicId>` | Today's shared invoice page | `documentCard` (unchanged) |
| `/receipts/<publicId>` | Today's shared receipt page | `documentCard` (unchanged) |
| `/bookings/<publicId>` | New booking page | `bookingCard` (new) |
| `/bookings/<publicId>/calendar.ics` | Calendar file for a confirmed booking | none |

Invoices, receipts and bookings get a random, unguessable `publicId`; services stay public by
slug. Old `/i` and `/r` links redirect. The new links reach people through chat replies,
customer emails, the post-checkout page and the owner's dashboard rows.

## Decisions (settled during brainstorming)

| Question | Decision |
| --- | --- |
| What to deliver, given `/book`, `/i`, `/r` exist | Literal `/services/:id`, `/invoices/:id`, `/receipts/:id`, `/bookings/:id` routes as the public URLs. |
| Unguessable part for private records | New random `publicId` column on `Invoice`, `Receipt`, `Booking` (migration + backfill). Not slug + HMAC key. |
| `/services/:slug` vs the `/book/:slug` flow | A new service profile page that hands off to `/book/:slug`. The booking flow, its URL and `/book/:slug/done` are unchanged. |
| Booking page actions | View, "Add to calendar" (`.ics`), "View receipt" once paid, "Book again" when over or cancelled. No customer cancel or reschedule. |
| Service page content | The service, its booking terms, and up to six other live services from the same business. No gallery. |
| Entry points | All four: chat replies, customer booking emails, post-checkout page, owner list rows. Chat "Share a service" sends `/services/<slug>`. |
| Route organisation | New `src/app/(public)/` route group beside `(app)`; middleware gates only the exact list paths. Next rewrites were rejected (two URL systems). |
| Visual language | Sara v1 Impeccable (`DESIGN.md`), extended, not replaced. Light only. |

## Goals

- A customer who is sent any Sara link (service, invoice, receipt, booking) lands on a calm
  page that answers their one question at a glance, on a 375px phone inside WhatsApp's or
  Instagram's in-app browser.
- Every one of those links unfurls in a chat as a card about that record, not the site card.
- A booking has a page: when, where, paid or not, add it to my calendar, find my receipt.
- No invoice, receipt or booking URL can be guessed from another.
- Every invoice and receipt link already sent keeps working.

## Non-goals

- Customer cancel or reschedule, or resuming an unpaid checkout.
- Online invoice payment ("Pay now" on an invoice).
- Business profile pages (`/b/<business>`), service galleries, reviews.
- Changing the `/book/<slug>` flow or its URL.
- Owner controls on public pages (a signed-in owner sees the same page a customer sees).
- Dark mode (DESIGN.md: white canvas, no dark sections).
- Backfilling receipt links for bookings paid before this ships.

## Data model

```prisma
model Invoice {
  // ...
  publicId String @unique @default(nanoid(16))
}

model Receipt {
  // ...
  publicId String @unique @default(nanoid(16))
}

model Booking {
  // ...
  publicId String    @unique @default(nanoid(16))
  payments Payment[]
}

model Payment {
  // ...
  bookingId String?
  booking   Booking? @relation(fields: [bookingId], references: [id], onDelete: SetNull)

  @@index([bookingId])
}
```

- `nanoid(16)` is generated by Prisma Client (Prisma 6.19 accepts it; checked with
  `prisma validate`). 16 URL-safe characters, 96 bits.
- `Payment.bookingId` lets a booking find its receipt (`booking → payments → receipt`). Today a
  booking's payment carries no link back to it; the Paystack webhook only knows the booking
  from transaction metadata.

### Migration

One migration, `add_public_ids`:

1. Add `publicId` as nullable `TEXT` to `Invoice`, `Receipt`, `Booking`.
2. Backfill existing rows in SQL. Postgres 16 has `gen_random_uuid()` built in, so no
   extension is needed:
   `translate(substr(encode(decode(replace(gen_random_uuid()::text, '-', ''), 'hex'), 'base64'), 1, 16), '+/', '-_')`
3. `SET NOT NULL` and a unique index on each.
4. Add `Payment.bookingId` (nullable), its foreign key (`ON DELETE SET NULL`) and index.

No backfill for `Payment.bookingId`: older bookings simply show no "View receipt".

## Link building — `src/server/share.ts`

`share.ts` becomes the one place public URLs are built:

```ts
export type PublicKind = "invoice" | "receipt" | "booking";
export function publicPath(kind: PublicKind, publicId: string): string; // "/invoices/<id>"
export function publicLink(kind: PublicKind, publicId: string): string; // absolute, from appBaseUrl()
export function servicePath(slug: string): string;                      // "/services/<slug>"
export function serviceLink(slug: string): string;
```

- Every current `shareUrl(kind, slug)` caller switches to `publicLink(kind, publicId)`:
  `api/invoices` (POST response `shareUrl`), `api/receipts` (same), the Paystack webhook,
  `messaging/dispatch`, `email/documents`. Each selects `publicId` alongside what it already
  reads. The API response field stays named `shareUrl`.
- The HMAC signer stays, renamed in comments as legacy-only: `isShareKey` verifies old links.
  `sharePath`/`shareUrl` are deleted once no caller remains.

## Routing

### Route tree

```
src/app/(public)/
  services/[slug]/        page.tsx  loading.tsx  not-found.tsx  opengraph-image.tsx
  invoices/[publicId]/    page.tsx  loading.tsx  not-found.tsx  opengraph-image.tsx
  receipts/[publicId]/    page.tsx  loading.tsx  not-found.tsx  opengraph-image.tsx
  bookings/[publicId]/    page.tsx  loading.tsx  not-found.tsx  opengraph-image.tsx
  bookings/[publicId]/calendar.ics/route.ts
```

`(app)/invoices/page.tsx` (owner list at `/invoices`) and `(public)/invoices/[publicId]/page.tsx`
resolve to different paths, so Next allows both. The plan's first task proves this with a
build before anything else depends on it. The `(public)` group has no layout of its own; the
root layout applies, as it does for `/book`, `/i` and `/r` today.

All four pages are `force-dynamic` (statuses and payments change after a link is sent).

### Middleware

`config.matcher` narrows from `"/invoices/:path*"` (and likewise for bookings, receipts,
services) to the exact list paths `"/invoices"`, `"/bookings"`, `"/receipts"`, `"/services"`.
`/dashboard/:path*`, `/settings/:path*` and `/onboarding` are unchanged. The middleware
therefore never runs for `/invoices/<id>`: no sign-in redirect and no generic bot card.
`destinationCard()` is unchanged; it is only reached for matched paths.

### Legacy links

`/i/[slug]/[key]` and `/r/[slug]/[key]` keep their routes but only redirect:

```ts
// src/server/legacy-links.ts
export async function legacyDocumentTarget(
  kind: "invoice" | "receipt", slug: string, key: string,
): Promise<string | null>; // "/invoices/<publicId>" or null
```

It checks `isShareKey(kind, slug, key)`, looks up `publicId` by slug, and returns the new path.
The page calls `permanentRedirect()` (308) on a hit and `notFound()` otherwise, keeping today's
not-found copy. Their `opengraph-image.tsx` files are deleted; unfurlers follow the redirect.

## Server loaders

New and moved functions in `src/server/`, all wrapped in React `cache()` so a page, its
metadata and its card share one query per request:

| Function | Returns | Null when |
| --- | --- | --- |
| `getSharedInvoice(publicId)` | `SharedDocument` (shape unchanged) | unknown id |
| `getSharedReceipt(publicId)` | `SharedDocument` | unknown id |
| `getServicePage(slug)` | `ServicePage` | unknown slug or paused service |
| `getPublicBooking(publicId)` | `PublicBooking` | unknown id |

- The invoice and receipt loaders change from `(slug, key)` to `(publicId)`; their key check
  moves to `legacyDocumentTarget`.
- `getServicePage` is a new catalog read with no availability work (unlike
  `getPublicService`, which computes slots for `/book`). `ServicePage`: the service's public
  fields (`slug, name, description, image, price, duration, currency, bookingMode,
  checkInTime, checkOutTime, minUnits, maxUnits`), `business: { name, city }`, and
  `others`: up to six other active services of the same business, newest first, each
  `{ slug, name, image, price, duration, bookingMode }`.
- `PublicBooking`: `publicId, status, startTime, endTime, units, holdExpiresAt, amount,
  currency, clientName`, `service: { slug, name, bookingMode, checkInTime, checkOutTime }`,
  `business: { name, address }` (address joined from `address, city, state` as the reminder
  email does), and `receiptPath` (`/receipts/<publicId>` of the newest receipt on the
  booking's payments, or null).
- No loader selects a phone number or an email address. Tests assert the `select` shape.

### Booking state — `src/utils/booking-view.ts` (pure)

```ts
export type BookingView =
  | "upcoming"   // CONFIRMED, start in the future
  | "past"       // CONFIRMED, start passed
  | "done"       // COMPLETED
  | "held"       // PENDING, hold not expired
  | "released"   // PENDING, hold expired, or no hold recorded (pre-hold bookings)
  | "cancelled"; // CANCELLED
export function bookingView(booking: Pick<PublicBooking, "status" | "startTime" | "holdExpiresAt">, now: Date): BookingView;
```

Two clocks, kept apart: `startTime` is Lagos wall-clock written as UTC, so it compares with
`wallClockNow(now)` from `backend/services/booking/clock.ts`; `holdExpiresAt` is a real
instant (`holdExpiresFrom(new Date())`), so it compares with `now` directly.

### Calendar file — `src/utils/ics.ts` (pure)

`bookingIcs(booking, { url })` returns a one-event `VCALENDAR`:

- `DTSTART`/`DTEND` as **floating local times** (no `Z`, no `TZID`). Slot times are stored as
  UTC wall-clock, so the stored digits are the local time the customer was shown.
- `UID: <publicId>@sara`, `SUMMARY: <service> with <business>`, `LOCATION:` the business
  address when set, `URL:` the booking page, `DTSTAMP` now (UTC).
- Text values escaped per RFC 5545 (`\`, `;`, `,`, newlines); lines folded at 75 octets.

The route answers `text/calendar; charset=utf-8` with
`content-disposition: attachment; filename="booking.ics"`, `cache-control: no-store`, and 404
unless the booking's view is `upcoming`.

## Pages

### Design read

Customer-facing detail pages for people a Lagos service business sent a link to, opened on a
phone inside a chat app's browser, in Sara's established v1 Impeccable world; they extend the
`/book` and shared-document page family. Visitor mode: Operate/Read (check a fact, take one
action); the service page leans Persuade.

- Dials: `DESIGN_VARIANCE 4`, `MOTION_INTENSITY 3`, `VISUAL_DENSITY 3`. Motion is the existing
  `animate-rise*` entrance only, already reduced-motion safe.
- Light only; DESIGN.md wins over taste-skill's dark-mode default.
- Copy: no em dashes, at most one `·` per line, "NGN 15,000" money form, sentence case, no
  eyebrows.
- Tailwind utilities on the existing tokens only (`CLAUDE.md`).

### Shared shell — `src/components/public/public-page.tsx`

Extracted from the markup `SharedDocumentPage` and `BookingPageClient` repeat inline:

```tsx
<PublicPage businessName="Tolu's Hair Studio" credit="Bookings" width="narrow" | "wide">
  {children}
</PublicPage>
```

- 64px header with the business name (`text-muted text-[15px] font-medium`, truncating).
- `narrow` = `max-w-[640px]` (documents, bookings); `wide` = `max-w-page` (services).
- Footer: "`{credit}` by" + single-ink `Wordmark`, `text-faint`, as on the document page.
- `SharedDocumentPage` adopts it; `/book` is left alone (non-goal).

### `/services/[slug]`

Hierarchy, phone first:

1. Photo at 16:10, `rounded-shot`, `next/image` with `priority` (the LCP element). No photo:
   no panel, no placeholder; text leads.
2. Name: headline type (Bricolage 400, `clamp(1.9rem, 1.3rem + 2.2vw, 3rem)`, -0.035em).
3. Price and length on one line: "NGN 25,000 · 4 hr"; stays and rentals: "NGN 85,000 per night".
4. Description, muted, max 60ch, line breaks kept. Omitted when empty.
5. Terms as a plain definition list with one hairline above (no card), built from the
   service's own fields (example values shown):
   - `SLOT`: Length: `formatDuration(duration)` ("4 hr").
   - `NIGHTLY`: Check-in from `checkInTime`. Check-out by `checkOutTime`. Stays of
     `minUnits` to `maxUnits` nights ("2 to 14 nights").
   - `DAILY`: Days run 24 hours from pickup. Rentals of `minUnits` to `maxUnits` days.
   - When `minUnits === maxUnits` it reads "Stays of 3 nights" / "Rentals of 1 day", never
     "3 to 3".
6. "More from {business}": up to six rows (thumbnail when the service has a photo, name,
   price and length), each linking to `/services/<slug>`; one column on phones, two from
   700px. Hidden when `others` is empty.

The one primary action, labelled by mode ("Book a time" / "Book your stay" / "Book your
rental", the `/book` page's own labels), links to `/book/<slug>`:

- Below `lg`: a fixed bottom bar, as on `/book` (page gets bottom padding to clear it).
- From `lg`: inline under the price line; the bar is not rendered.
- Layout from `lg`: `/book`'s grid, copy left, photo right (`lg:grid-cols-[1fr_460px]`);
  without a photo, a single column. "More from" spans the full width below.

Not found (unknown or paused): "This service isn't taking bookings." / "It may have been
paused or renamed. Ask the business for a fresh link."

### `/bookings/[publicId]`

Narrow column, phone first:

1. `StatusPill` from `BOOKING_STATUS` (pending reads "Awaiting payment").
2. Service name as the headline. Under it, muted: "With {business}. Booked for {clientName}."
3. **The when panel** (the page's focal point, real product content): `bg-surface
   rounded-panel`, read like a calendar leaf.
   - `SLOT`: "Sat 12 Oct" in stat type (Bricolage 330), "2:00 pm to 6:00 pm" below.
   - `NIGHTLY`: two halves, "Check-in" / "Check-out", each a date in title type and its time
     in muted text; "3 nights" beneath.
   - `DAILY`: "Pickup" / "Return", same shape; "2 days" beneath.
   - Then a hairline and rows: **Where** (business address; row omitted when none), **Paid**
     (or **To pay** while held) with the amount.
4. Actions and copy by `bookingView`:

| View | Line under the panel | Primary | Secondary |
| --- | --- | --- | --- |
| upcoming | none | Add to calendar (`calendar.ics`) | View receipt (when `receiptPath`) |
| past | none | none | View receipt; Book again |
| done | none | none | View receipt; Book again |
| held | "We're confirming your payment. Your time is held for 30 minutes." | none | none |
| released | "Payment didn't come through, so this time was released." | Book again | none |
| cancelled | "This booking was cancelled." | Book again | none |

"Book again" links to `/book/<service-slug>`. One primary per view (taste: no duplicate CTA
intent). Not found: "We couldn't find that booking." / "Check the link in your confirmation
email, or ask the business to send it again."

### `/invoices/[publicId]`, `/receipts/[publicId]`

`SharedDocumentPage` unchanged in content and layout, wrapped in `PublicPage`. Not-found copy
is today's ("This link is wrong or no longer works…").

### Loading and errors

- Each route's `loading.tsx` is a skeleton in the page's own shape (as `/book/loading.tsx`).
- A loader that throws renders `PublicError` ("This booking didn't load." / "Something went
  wrong on our side. Refresh the page to try again.") and logs `console.error("[bookings] …")`,
  matching `/i` and `/book`.

## Share cards — `src/server/og.tsx`

All 1200×630, Satori, the existing grid: 64px padding, a flexible left column, a 420px panel
on the right, Bricolage and Hanken from `assets/fonts`. Any unknown record, or any error,
renders `pageCard("site")`.

- **`serviceCard(service)`**: today's `/book/[slug]/opengraph-image.tsx` body moved into
  `og.tsx` (photo fetch with the 4s timeout and `sharp` crop included). The pill follows the
  mode: "Pick a time" / "Pick your dates" / "Pick your days". `/book/[slug]` and
  `/services/[slug]` both call it.
- **`bookingCard(booking)`** (new):
  - Left: business name (Hanken 600, 28px, muted), service name (Bricolage, 76px, or 60px past
    28 characters), then at the foot the status pill (tones as `documentCard`'s `PILL`) and
    "Bookings by" + single-ink `OgLockup`.
  - Right, the calendar leaf on `OG.surface`, `borderRadius 32`:
    - `SLOT`: weekday and month (Hanken 600, 26px, muted) at the top; the day number in
      Bricolage 400 at about 200px, ink; the start time (Hanken, 30px) below.
    - `NIGHTLY` / `DAILY`: start date over end date (Bricolage, 56px) with "to" between in
      muted Hanken, then "3 nights" / "2 days".
  - Never shows the customer's name or the amount (cards get forwarded into group chats).
- **`documentCard`**: unchanged; the new invoice and receipt routes call it.

## Metadata

All through `pageMetadata()`; the card is the segment's `opengraph-image`.

| Route | Title | Description | Index |
| --- | --- | --- | --- |
| `/services/<slug>` | "{service} · {business}" | SLOT: "NGN 25,000 for 4 hr with {business}. Pick a time and pay with Paystack." NIGHTLY/DAILY: "NGN 85,000 a night with {business}. Pick your dates and pay with Paystack." | yes |
| `/bookings/<id>` | "{service} with {business}" | upcoming/past: "Confirmed for Sat 12 Oct, 2:00 pm." held: "Confirming payment for …" released/cancelled: "This booking is no longer active." done: "Done on Sat 12 Oct." | no |

## Entry points

- **Chat**: invoice and receipt links via `publicLink` (dispatch); the owner's
  "💰 … paid" notice links the new receipt URL; `bookingLinkText` sends `serviceLink(slug)`.
- **Customer emails** (`email/messages.tsx`, templates):
  - `bookingConfirmedEmail` gains `bookingUrl`; its `CtaButton` becomes "View your booking";
    the receipt becomes a secondary text link "View your receipt" when present.
  - `bookingReminderEmail` and `bookingRescheduledEmail` gain `bookingUrl` and a "View your
    booking" `CtaButton`.
  - `bookingCancelledEmail` unchanged ("Pick another time" to `/book`).
  - Senders pass `publicLink("booking", booking.publicId)`: the Paystack webhook, the
    `booking-reminders` cron, and `api/bookings/[slug]` (reschedule).
- **Post-checkout** (`/book/[slug]/done`): `getBookingReceipt` also returns `publicId`; the
  confirmed state adds a secondary "View your booking" button.
- **Paystack webhook**: `paymentData` gains `bookingId`.
- **Owner dashboard**:
  - Invoice, receipt and booking rows each get the existing `CopyLinkButton` for their
    public link. Rows already receive the full model through the DTOs, so `publicId` arrives
    with the column; each list page passes a `publicBaseUrl` prop, as `services/page.tsx`
    passes `bookingBaseUrl` today.
  - `ServiceCard` shows and copies `/services/<slug>` instead of `/book/<slug>`.
  - The document modal's post-create link is the API's `shareUrl`, so it updates on its own.
- **Docs**: `PRODUCT.md` "Booking links" line gains the service page; `DESIGN.md` Logo
  section's "Share cards" list gains the service and booking cards.

## Error handling

| Case | Behaviour |
| --- | --- |
| Loader throws | `PublicError` with the route's copy; `console.error` tagged by route. |
| Unknown id, paused service | `notFound()` with the route's `not-found.tsx`. |
| `opengraph-image` loader throws or record missing | `pageCard("site")`. |
| Service photo fetch fails or times out (4s) | Card falls back to the mark on leaf grey (today's behaviour). |
| `calendar.ics` for a non-upcoming or unknown booking | 404. |
| Legacy `/i` or `/r` with a bad key or unknown slug | Not-found page, as today. |
| Receipt creation fails in the webhook | Booking still confirmed; page shows no "View receipt" (today's best-effort rule). |

4. `PublicPage` shell; invoice and receipt routes; legacy redirects; old OG files removed.
5. `serviceCard` extraction; service page, loading, not-found, metadata.

7. Entry points: webhook `bookingId`, emails, done page, chat, owner rows, service card.
8. Docs (`PRODUCT.md`, `DESIGN.md`) and the verification run.
